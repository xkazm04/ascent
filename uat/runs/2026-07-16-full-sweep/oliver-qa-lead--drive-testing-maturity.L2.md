## 2. Findings

### Finding L2-1 — Systemic org-scope mismatch: public-funnel scans vanish from their own permalink, /trends, and the recommendation tracker
- id: L2-oliver-drive-testing-maturity-004
- journey: drive-testing-maturity · character: Oliver · cert_level: L2
- type: broken-flow
- severity: major (derived from impact below)
- dimension: trust / completion
- **NEW at L2** — not predicted by L1's surface model (L1 assumed a persisted scan reliably resolves at its own permalink; it does not, under this env's actual config).
- impact: `{ frequency: high — happens on every public-funnel scan revisit in this environment, not an edge case; reachability: high — hit via the journey's own described entry point (paste a public repo from "/"); trust_erosion: high — the report, the trend line, and the tracker all independently claim "never scanned" about a scan Oliver just watched complete }`
- expected: revisiting `/report/vercel/swr`, `/trends?repo=vercel/swr`, and `GET /api/recommendations?repo=vercel/swr` after a completed public scan should reliably serve the persisted report/trend/recommendations.
- got: all three return empty/"not scanned" states. Root cause traced in code: `readableOrgForOwner(owner)` (`src/lib/auth.ts:353-358`) and the identical inline pattern in `/api/recommendations` (`src/app/api/recommendations/route.ts:40-41`) resolve the read-side org scope via `canReadOrg(owner)` (`src/lib/authz.ts:141-155`), which — under this env's `ASCENT_OPEN_ORG_DASHBOARDS=1` + the auth-bypass's `!authGateEnabled()` — returns **true for literally any owner login**, seeded org or not (`authz.ts:153`, `openOrgDashboardsEnabled()`). So every read resolves `orgSlug = owner.toLowerCase()`. Meanwhile the scan itself is always persisted under `orgSlug: "public"` (`src/app/api/scan/stream/route.ts:145`, `resolveScanAuth` in `src/lib/scan.ts:117-154` only returns a non-public orgSlug when a *real GitHub App installation* can mint a token — never true for an ordinary public-funnel scan). `getScanReportByCommit` then calls `resolveOrgId(orgSlug)` (`src/lib/db/scans-read.ts:801-802`) against an org slug that was never actually seeded (e.g. "lukeed") or that IS seeded but scopes a different tenant than where the scan lives (e.g. "vercel") — either way `resolveOrgId` returns null or a real-but-wrong org, and the lookup comes back empty. The same root cause propagates to `/trends` (`src/app/trends/page.tsx:81`, same `readableOrgForOwner` call) and recommendations.
- evidence: live reproduction — `vercel/swr` scanned live via `POST /api/scan/stream` (209s, claude-cli, confirmed `x-ascent-cache: hit` on a subsequent `GET /api/scan?peek=1`), then `/report/vercel/swr` → "No report yet"; `/trends?repo=vercel/swr` → "We haven't stored any scans"; `GET /api/recommendations?repo=vercel/swr` → `{"scanId":null,"items":[]}`. Repeated with `lukeed/clsx` (no org relationship at all) with identical results, ruling out "org-name collision" as the sole trigger. `src/lib/auth.ts:353-358`; `src/lib/authz.ts:141-155`; `src/app/api/scan/stream/route.ts:145`; `src/lib/scan.ts:117-154`; `src/lib/db/scans-read.ts:801-802`; `src/app/trends/page.tsx:81`; `src/app/api/recommendations/route.ts:40-41`.
- code_check: present-broken (not by-design — the persist path and the three read paths use two different, unreconciled org-resolution strategies for the exact same repo).
- verdict: confirmed (adversarial check: is this just a dev-bypass quirk that can't happen in production? No — `canReadOrg`'s production branch checks *real* membership, but a real org member who scans a same-owner public repo via the free/anonymous funnel — never installing the GitHub App for it — hits the identical mismatch: `readableOrgForOwner` resolves their real org, `resolveScanAuth` still persisted under "public". The dev bypass just makes it reproduce for *every* owner login instead of only real members', which is why it surfaced here on the very first two repos tried.)
- scope_note: this environment's `ASCENT_OPEN_ORG_DASHBOARDS=1` amplifies the failure rate (any owner string "passes" `canReadOrg`) — a production deployment would only hit this for a signed-in real org member scanning a same-owner public repo, a narrower but still real slice of users.
- suggested_acceptance: either (a) have the read paths (`getScanReportByCommit`, `/trends`, recommendations) fall back to `orgSlug: "public"` when the member-scoped lookup comes up empty, mirroring the persist-side default, or (b) make `resolveScanAuth`'s org resolution and `readableOrgForOwner`'s org resolution provably the same function for the same repo, so persist-scope and read-scope can never diverge.

### Finding L2-2 — Recommendation-tracker save failures on a permanently-blocked action are worded as retryable ("check your connection")
- id: L2-oliver-drive-testing-maturity-005
- journey: drive-testing-maturity · character: Oliver · cert_level: L2
- type: quality-gap
- severity: minor (derived from impact — real but secondary to L2-1, and only reachable once L2-1 is fixed)
- dimension: clarity / trust
- **NEW at L2**, code-cross-checked but not independently click-verified live (L2-1 prevented ever reaching a loaded public-org recommendation row to click on — see caveat below).
- impact: `{ frequency: medium — only hit on the public/anonymous funnel, not org-context scans; reachability: high once L2-1's dead-end is worked around; trust_erosion: medium — a permanent policy block presented as a network hiccup invites a user to retry forever }`
- expected: attempting to change a recommendation's status on a public-funnel (anonymous) scan should either not offer the control, or fail with a message that says tracking isn't available for this scan (mirroring the existing "config" wording used for the no-DB 503 case).
- got: `PATCH /api/recommendations/[id]` explicitly 403s any status/assignee/date change on a recommendation whose owning scan is org `"public"` (`src/app/api/recommendations/[id]/route.ts:45-50` — "Recommendation tracking is available for your own organization's scans."), but the client only special-cases a `503` as the non-retryable "config" case (`src/components/report/RecommendationTracker.tsx:98-107`) — a `403` falls into the generic "transient" bucket and shows "Couldn't save that change. Check your connection and retry," which will never succeed no matter how many times it's retried. The `<StatusSelect>` control itself is rendered identically regardless of the owning scan's org scope — no read-only affordance exists for the public funnel.
- evidence: `src/app/api/recommendations/[id]/route.ts:45-50` (the 403 + message); `src/components/report/RecommendationTracker.tsx:98-116` (the kind-classification that maps 403 → "transient" → "check your connection and retry"). Live: the PATCH state machine itself was confirmed to genuinely work end-to-end on an *org-scoped* recommendation (`vercel/next.js`, open→in_progress→done, actor-attributed event timeline) — the 403 path is a code-traced sibling of that same endpoint, not independently fired against a live public-org row, because L2-1 prevented any public-funnel scan from ever having a loaded recommendation row to click in this session.
- code_check: present-broken (message taxonomy doesn't cover this real status code)
- verdict: confirmed, with the caveat above (medium confidence — inferred from the same code path that DID get exercised live for the org-scoped case, not from clicking the exact 403 in a browser this session).
- suggested_acceptance: add a `kind: "policy"` bucket for 403 (or any non-503, non-409, non-network failure carrying a stable server message) with its own honest copy, and hide/disable the status control entirely for public-org recommendations rather than showing a live, clickable dropdown that always fails.

### Finding L2-3 — D2 gate floor: confirmed discoverability gap, not a missing-feature gap
- id: L2-oliver-drive-testing-maturity-001 (L2 confirmation of L1-001)

- verdict: confirmed as **discoverability, not missing-feature** — the exact outcome L1's `l2_priority` asked to resolve. A savvy Oliver (or an SDET who reads the API) *can* gate on testing today by hand; an ordinary Oliver using only the governance UI cannot.

- suggested_acceptance: unchanged from L1 — extend `GatePolicyEditor` with a generic per-dimension floor picker, or add a dedicated "Testing floor (D2 ≥)" control alongside Security's.

## 4. Character voice — first-person verdict

Alright. The read itself is the best part of this whole session — genuinely. I fed it a real repo, it came back in under four minutes with a testing-maturity paragraph that names the test-to-source ratio, the exact e2e edge cases covered, AND the one gap (no mutation testing) that a coverage number would have hidden from me. That's not a demo trick; that's the assessment I'd have written after a day with the repo cloned. Same for D8 — it correctly told me "no AI usage" and "no AI test harness" are different questions, and answered the harness one honestly (there isn't one, here). If the session had ended there, I'd be drafting the rollout email to my squads.

It didn't end there. I came back to the same report five minutes later — the way I'd actually work, since nobody reads a maturity report and immediately closes the laptop — and the tool told me the repo had never been scanned. Then the trend line told me the same lie. Then the recommendation tracker had nothing in it at all, not even the items I'd just read in the roadmap. Three surfaces, three independent "you imagined that" responses about a scan I watched complete with my own eyes. I dug into why (I know enough to read a stack trace, and I traced this one to the actual source), and it's a real bug — the app persists a public scan under one bucket and reads it back looking in a different one, and that mismatch isn't some obscure edge case, it's the very first thing that happens when a real user with a real org membership scans a public repo. That's not a "wait for the next release" gap. That's the artifact I need to walk into my VP's office with — gone, on reload.

The gate mechanism redeemed itself a little: I went and tested it directly, the way I'd test any tool I was about to bet a policy on, and the underlying enforcement is real — I made it fail a merge on a dimension floor and watched the 422 come back with the exact right reason. Somebody just didn't wire the UI up for testing the way they did for security. I can work around that with an API call if I have to. I can't work around a report that forgets it exists.

Would I adopt it? For the *read itself* — yes, without reservation, that's genuinely better and faster than my spreadsheet, and I'd trust it enough to skip my manual audit on future repos. Would I roll it out to my six squads as *my* enforcement and tracking system, today? No — not until the report/trend/tracker actually persist reliably across a session, because right now the thing I need to prove to my VP that testing maturity moved is exactly the thing that vanishes the moment I look away.
