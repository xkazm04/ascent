# Implementation design — UC2 "Registry" and UC3 "Care" in the org dashboard

_2026-08-17. Implementation companion to [`GOLDEN-USE-CASES.md`](GOLDEN-USE-CASES.md) (the strategy
+ cloud topology). This doc says what gets built, where, in what order, and how the tabs look. It is
the brief the prototype builders and the ship-loop milestones read._

## 0. Decisions this doc fixes

1. **The registry is a customer-owned repo; ascent onboards, indexes and tracks it.** Skills,
   Practices and Memory move *out of* ascent's tables as source of truth and *into* the registry
   repo. Ascent keeps mirror rows (the index) so every existing read surface keeps working.
2. **A new tab module `Registry` under the `Shared` group** (renamed from `Chosen`, see §0b) (`?tab=registry`), sitting first in the
   group: it is the onboarding step the other three depend on, and their sync-health strip links back
   to it. Group order becomes: Registry · Practices · Skills · Memory · Governance · Developer
   (Plan/Backlog were retired for Follow-ups by a parallel change on 2026-08-17).
3. **Developers talk to the registry with git, outside ascent's control.** `npx ascent …` is a
   convenience over plain git (sync = pull, push = branch + PR); a developer with only `git` and a
   text editor is a first-class citizen. Ascent learns about changes by indexing (webhook + scan),
   never by being in the write path.
4. **UC3 is not "a skill outside ascent".** The local `/mentor` skill is the *sensor and coach*
   (it must run where the developer's sessions are); **ascent is the memory, the map and the bridge**
   — the developer's home at **`/org/developer`** (personalized to the signed-in user, presented as a
   "Developer" rail item, not a `?tab=` panel) and the anonymized care aggregate inside Contributors.
   §5 argues why the app is the reason the skill is worth running; §5.1–5.4 record the 2026-08-18
   decisions (Companion won; React-state routing; route + Contributors relation).
5. **Prototype every new tab with three directional variants** (`/prototype`, worktree, Opus builders),
   pick, consolidate. Registry and Care each get a prototype round before any data-layer work beyond
   the read model they need.

## 0b. Nav + code-structure decisions (2026-08-18)

1. **The `Chosen` group is renamed `Shared`** — it holds the org's *shared primitives*: the registry
   and everything it distributes (Plan · Practices · Skills · Memory). "Chosen" described a question
   ("what did we decide our way of working is?"); "Shared" describes what the group actually contains.
2. **Governance moves to `Standing`.** It is a statement of where the org *stands* (branch protection,
   required reviews, the AI stance), not a shared primitive the registry distributes.
3. **Developer leaves the rail and lives behind the header username.** It is per-person, not per-org:
   it hangs off the identity, opened from the header menu (`/org/developer`). It stays in
   `ORG_TAB_IDS` (route, label, a11y contract) and joins `ORG_TABS_NOT_IN_NAV`.
4. **Client code mirrors the UI hierarchy**: `src/features/<nav-group>/<tab>/…`
   (`src/features/standing/governance/GovernanceTab.tsx`), sub-folders for larger features, **max 200
   LOC per file** under `src/features/**` (the repo-wide 300-LOC rule still governs everything else).
   Shared/cross-cutting components are explicitly excluded and stay put (`src/components/ui`,
   `src/components/org/shared`, `src/components/org/shell`).
5. **Registry actions are capability-gated, never decorative.** `getRegistryView` carries a
   `capabilities` block (app configured · installation present · token mintable · viewer role ·
   can-create-repo). If ascent cannot act on the user's behalf, the GitHub buttons and links are **not
   rendered at all** — no dead affordance, no silent failure. When it can, the action opens a real PR
   through the existing `openDraftPr` path.
6. **Practices · Skills · Memory read their state from the registry.** Unmapped ⇒ each tab shows the
   same honest empty state pointing at Registry; mapped ⇒ content comes from the indexed mirror rows,
   and the write affordances follow `origin` (hosted rows keep in-app forms; registry rows offer
   "Open in registry" / "Propose change (PR)").
7. **A real example registry** lives at `github.com/xkazm04/ai-registry` — the fixture the integrations
   are wired and tested against (it carries one deliberately drifted skill version so `stale` shows up).

## 1. The registry repo (v1 layout, scaffolded by ascent)

```
<org>/ai-registry/                     # default name; any repo can be mapped
  README.md
  .ascent/registry.yaml                # {registry: 1, canonical: true, mode: git-native|hosted-mirror,
                                       #  telemetry: api|registry|off, policies:{requireDescription, requireVersion,
                                       #  categories:[…], memoryKinds:[…]}, owners:[…]}
  catalog.json                         # GENERATED by ascent (bot commit or PR per policy): the index everyone syncs
  skills/<name>/SKILL.md               # frontmatter contract (name, description, category, memory, version)
  skills/<name>/LESSONS.md             # append-only reflection lane 2
  practices/<slug>/PRACTICE.md         # the leak-free SHAPE (frontmatter: id, dimension, applies-when) + starter/ files
  practices/<slug>/starter/**          # templatized starter artifacts (what practice-artifact.ts generates today)
  memory/<kind>/<slug>.md              # Org Memory notes: frontmatter {kind, confidence, namespace, supersedes?, source}
  memory/_index.md                     # generated MOC (Obsidian-navigable)
  telemetry/<repo>/<yyyy-mm>.jsonl     # only when telemetry: registry — counts only
  CODEOWNERS                           # merging = adopting
```

- One canonical registry per org; additional registries (team-level) allowed, each mapped, each
  indexed; the fleet views merge them with the canonical winning on name collision.
- Personal workspaces get the same layout in `<user>/ai-registry` (all three tabs already exist in
  personal nav; Registry and Care are added — see §4/§5).
- Every fleet repo points at its registry from `.ai/manifest.yaml → skills.registry` (spec 0.1→0.2,
  additive). Missing pointer ⇒ the org's canonical registry is assumed.

## 2. Data model (Prisma) — additive, migrate-on-read where possible

```prisma
model OrgRegistry {                     // one row per mapped registry repo
  id, orgId, repositoryId?              // Repository row of the registry repo (role = "registry")
  fullName, defaultBranch, canonical Boolean, mode enum(git_native, hosted_mirror)
  telemetrySink enum(api, registry, off)
  status enum(unmapped, scaffolding, scaffold_pr_open, indexed, error), lastIndexedAt, lastIndexSha
  catalogSha, webhookHealthy Boolean, policiesJson
  migration Json?                       // {skills: n/n, practices: n/n, memory: n/n, prUrl, state}
}
// mirror columns on existing rows
OrgSkill        += origin enum(hosted, registry), registryId?, registryPath?, registryHash?, registryVersion?
OrgMemory       += origin, registryId?, registryPath?, registryHash?
OrgPracticeShape+= origin, registryId?, registryPath?, registryHash?
OrgSkillLesson    { skillId, versionUsed, date, repo, bullets Json, redesign Boolean, registryPath }
OrgSkillEvent.source enum(cli, hook, ci, web, registry)   // validated; `invoke` un-retired
Repository      += role enum(fleet, registry)              // registry repos are excluded from maturity math
```
Existing readers (`listOrgSkills`, `listOrgMemories`, practice-shape loaders) keep their signatures;
`origin` decides whether the row is writable in-app (hosted) or PR-only (registry).

## 3. Indexer + writers (server)

- **Indexer** `src/lib/registry/index-registry.ts`: given an `OrgRegistry`, fetch the tree at HEAD
  (existing GitHub read layer), parse `skills/*/SKILL.md` (reuse `skill-frontmatter.ts`),
  `practices/*/PRACTICE.md`, `memory/**/*.md`, `LESSONS.md`; upsert mirror rows keyed by
  `(registryId, registryPath)`; delete mirror rows whose path vanished (soft: `archivedAt`). Runs on
  the registry repo's push webhook (`src/app/api/app/webhook`), on any scan of that org, and from the
  tab's "Re-index" action. Writes `catalog.json` back (bot commit if policy allows, else a PR).
- **Fleet adoption**: the repo scan already grades `.claude/skills`; extend the tree walk to hash each
  SKILL.md and match against catalog names+hashes → `OrgSkillAdoption` rows with
  `syncState in_sync|stale|diverged|local_only`.
- **Writers** (all PR-only in git-native mode, through the shared write path in
  `src/lib/practices/apply.ts` / `src/lib/github/write.ts`): `scaffoldRegistryPr` (initial layout +
  README + registry.yaml + CODEOWNERS), `migrateToRegistryPr` (exports current hosted OrgSkill /
  OrgPracticeShape / OrgMemory rows into the layout — one PR per artifact type so review stays
  readable), `proposeSkillPr` (Phase D candidate → PR from the exemplar), `rolloutPr` (per fleet repo).
- **API**: `POST /api/org/:slug/registry` (map / create), `POST …/registry/index`,
  `POST …/registry/migrate?type=skills|practices|memory`, `GET …/registry` (view model),
  `POST /api/org/skills/events` (existing; `invoke` restored). Token scope `registry:write` added to
  `SKILL_TOKEN_SCOPES` for the CLI's PR-opening path when the developer has no GitHub write access.

## 4. The `Registry` tab (module under Shared) — states and content

`src/features/shared/registry/RegistryTab.tsx` (server, `slug` prop, same shell contract as
SkillsTab/MemoryTab) → `RegistryPanel*` (client where interactive). Read model
`src/lib/org/registry-view.ts → getRegistryView(slug): RegistryView`:

```ts
type RegistryView = {
  status: "unmapped" | "scaffolding" | "scaffold_pr_open" | "indexed" | "error";
  registry?: { fullName; url; defaultBranch; canonical; mode; telemetrySink; lastIndexedAt; lastIndexSha; catalogSha; webhookHealthy };
  counts: { skills: {registry, hostedOnly}; practices: {registry, hostedOnly}; memory: {registry, hostedOnly}; lessons: number };
  migration: { skills: Step; practices: Step; memory: Step }   // Step = { state: "not-started"|"pr-open"|"merged"|"n/a"; prUrl?; moved; total }
  fleet: { reposTotal; reposPointing; reposSynced30d; adoption: { inSync; stale; diverged; localOnly } };
  activity: Array<{ at; kind: "skill-version"|"lesson"|"practice"|"memory"|"catalog"|"index"; title; url? }>;   // last 20
  telemetry: { invokes30d; reposReporting; sink };
  howTo: { syncCmd: "npx ascent skills sync"; hooksCmd: "npx ascent hooks install"; pointer: "skills.registry: github:<org>/ai-registry" };
};
```

**Unmapped state = the onboarding stepper** (the key step the user named). Steps, all resumable:
1. *Choose*: **Create `<org>/ai-registry`** (GitHub App creates + opens the scaffold PR) · **Map an
   existing repo** (picker over installed repos; validate layout, offer to scaffold missing parts by
   PR) · **Stay hosted** (explicit, dimmed; keeps today's behavior, shows what you give up).
2. *Permissions*: verify the App has contents:write on the chosen repo; else show the install link.
3. *Scaffold*: PR opened → wait for merge (poll/webhook) → `indexed`.
4. *Migrate*: three cards (Skills n · Practices n · Memory n) each with "Open migration PR" → merged
   → mirror rows flip `origin=registry`. Until merged, the corresponding tab shows a "hosted, not yet
   in registry" strip.
5. *Point the fleet*: show the manifest pointer + a "propose pointer PRs to N repos" action (uses the
   `.ai/` foundation PR path); "or developers run `npx ascent skills sync`".
6. *Verify*: first `catalog.json` written, first fleet repo synced, first invoke event → done.

**Indexed state = the registry dashboard**: header (repo link, canonical chip, mode, sink,
last indexed · sha, webhook health, Re-index); the three-artifact ledger (counts registry vs
hosted-only, migration state); fleet sync (pointing / synced / adoption breakdown, link to the Skills
heatmap); activity feed; developer how-to (copyable commands + pointer); policies summary; danger zone
(unmap / switch canonical).

**Prototype directions (three, one file set each behind a `RegistryPanelSwitcher`):**
- **Ledger / Index** — editorial single column: `Dateline` masthead, three-artifact ledger as
  `TILE_LEDGER` cells, the stepper as numbered index entries; the onboarding reads like a table of
  contents being filled in.
- **Blueprint / Instrument** — the registry as an engineering drawing: repo tree rendered as a mono
  file map (skills/ practices/ memory/ with counts and hashes), sync dials (`Meter`), status readouts;
  the stepper as a wiring diagram from ascent → registry → fleet repos.
- **Pipeline / Journey** — left-to-right flow ascent → registry → fleet → developers with live
  counters on each edge (index → catalog → sync → invoke); the stepper *is* the pipeline lighting up
  stage by stage; connected state shows throughput and stale edges.
Each variant must render both states (`?demo=indexed` toggles a fixture view model) and every edge
case (no App permission, PR open, index error, hosted mode).

## 5. UC3 in the app — the `Care` tab, and why the app is the point

The objection is right: if `/mentor` alone did the job, ascent would be a download page. It does not,
because the developer's problem is not "reflect once"; it is **carry the reflection across machines,
repos, weeks and teammates, and turn it into changes that stick.** The local skill is the only place
the raw signal exists (private, on-machine, no account needed — that boundary stays absolute); the
app is what makes the loop worth running:

| Local skill (sensor + coach) | Ascent app (memory + map + bridge) |
|---|---|
| mines transcripts (counts/shapes), interviews, writes `profile.md`, runs retros | keeps the **profile and journal history** across machines/reinstalls (the developer's data, personal workspace only) |
| proposes moves from a local catalogue | grounds moves in **cross-repo facts** the skill cannot see: the gaps of *every* repo the developer touches, the registry catalog, fleet evidence ("this skill saved 3 other repos 2 pts on D2") |
| can install a skill / open a CLAUDE.md PR *if given a token* | **opens the PR for you** (practice apply, skill install PR) and tracks it in the same Backlog you already own |
| one developer at a time | **the bridge to UC2**: a kept move → "promote to a registry skill" (PR to the registry, you as author) — champions emerge from evidence, not nomination |
| no comparison | **anonymous fleet baseline** (opt-in, floors): where your session shape sits vs the org, without anyone seeing you |
| trend on one machine | **the climb over time** — your personal trajectory chart (moves kept, habits protected, repos lifted) next to the org's |

So the value proposition for the developer is *"your coach remembers, sees your whole map, and can act"*;
for the org it is *"care produces registry content and adoption evidence you could not author top-down"*.

**`Care` tab (`?tab=care`)** — one id, two modes by `Organization.kind`:

- **Personal mode (the developer's home; the tab lands first in a personal workspace):** Profile
  card (what you shared, editable link back to local profile) · Moves board (proposed / trying /
  kept / dropped, each with evidence + expected saving; "promote to registry" on kept moves) · Session
  shape strip (30-day counts the developer chose to share: sessions, turns, plan-mode %, retries,
  tests-before-commit %) with anonymous org band if opted in · My repos' gaps (the repos you commit
  to, their open recommendations you could champion) · Journal (weekly retro lines) · Setup (`npx
  ascent mentor init`, hook status, what is/isn't shared — the privacy ledger).
- **Org mode (aggregate under floors, `CHAMPION_MIN_POP` etc.):** Care adoption (developers with a
  mentor set up / sharing, as counts) · Most-kept moves fleet-wide → "author as registry skill"
  candidates · Asks (anonymized interview themes: "where AI wastes my time") → registry backlog inputs
  · Session-shape distribution (bands, no individuals) · Outcome link (kept move → repo score delta,
  reusing `skill-outcomes`). Never a per-person row.

Read model `src/lib/org/care-view.ts → getCareView(slug, viewer): CareView` (personal: from
`PersonalMentorProfile`, `MentorMove`, `MentorJournal` rows written only by `POST /api/me/mentor/share`;
org: aggregates with floors). New tables are personal-scoped and capped like `personal.ts`.

**Prototype round result (2026-08-18): Companion won.** Climb and Cockpit are deleted; the Companion
variant is the render. Decisions taken with the pick:

### 5.1 The developer's home is a route, presented as a tab: `/org/developer`
- The Care module is **personalized to the authenticated developer**: every signed-in user sees
  *their own* activity (repos they commit to, their AI-attributed share, the gaps of their repos, their
  care loop), never someone else's. So it does not belong under `?tab=care` inside an org's panel set;
  it lives at **`/org/developer`** (static route; wins over `/org/[slug]`), org context via
  `?org=<slug>` (default: the viewer's first readable org, else their personal workspace).
- It is reached from the **header identity menu** (§0b.3), not the rail, so the whole left rail
  stays available on the route without a personal surface sitting inside org-scoped navigation: the page reuses the org shell (extract the `[slug]/layout.tsx` body
  into a shared `OrgShell` server component; the developer route renders the same header + rail with
  the `developer` item active). `orgTabHref(slug, "developer")` returns `/org/developer?org=<slug>`;
  `developer` is in `ORG_TAB_IDS` (for the rail/label/a11y contract) but is **not** a `?tab=` panel and
  has no `OrgTabChunks` branch — it is deliberately not mixed with the existing tabs.
  `/org/[slug]/developer` redirects to `/org/developer?org=<slug>`.
- The `care` tab id is retired (its org mode moves into Contributors, §5.2); `PERSONAL_TAB_IDS`
  carries `developer`.

### 5.2 Relation to Contributors (`?tab=contributors`)
Contributors is the **org's view of all developers** (git-side signals under the champion floors:
AI share, involvement, bus factor). The Developer route is the **developer's view of themself** — the
same signals for one login, unfloored because it is their own data, plus the private care loop that
only they can see and only they can share.
- Contributors gains a **"You" pointer**: if the viewer appears in the roster, their row carries
  "This is you → your Developer view"; if not (or below floors), a quiet strip "See your own activity
  → /org/developer".
- The former Care *org mode* (adoption counts, most-kept moves, asks, shape bands, outcomes — all
  floored, never a person) becomes a **Care section inside Contributors**, rendered from
  `getCareOrgAggregate(slug)` when population ≥ `CHAMPION_MIN_POP`; otherwise the honest suppressed
  state. Nothing per-person crosses from Developer to Contributors except through `share`.

### 5.3 Routing inside the module
Sub-views and fixture previews are **React state**, not search params: the Developer page is one
server-rendered shell handing the view model to a client `DeveloperHome`; any switching (fixture
"preview as" while there is no shared data, section focus, board filters) is `useState`. No `?demo=`.

### 5.4 Read model
`getDeveloperView(viewerLogin, orgSlug)`: real path today = the viewer's slice of
`getContributorInsights` (repos, commits, AI share, champion status) + the open recommendations of
those repos + an empty care loop (no `share` yet) — grounded, no fabrication. Fixtures are selected in
client state for preview only. Personal-scoped tables (`PersonalMentorProfile`, `MentorMove`,
`MentorJournal`) land in C3 and fill the loop.

## 6. Skills / Practices / Memory after the move

- Each tab gains a shared **`RegistrySyncStrip`** (from `RegistryView`): "Backed by
  `<org>/ai-registry` · indexed 4 min ago · 3 repos diverged" or "Hosted only — set up a registry →".
- Write affordances change by `origin`: hosted rows keep today's forms; registry rows show **"Open in
  registry"**, **"Propose change (PR)"** (opens a prefilled PR through the writer), and the frontmatter
  contract is validated by the indexer, not the form.
- Skills tab: fleet heatmap (repo × skill), Trace (versions from git history + lessons), candidate
  deck (Phase D). Practices tab: exemplar shapes read from `practices/`, apply = starter from the
  registry. Memory tab: notes read from `memory/`, recall unchanged (index rows), reflect proposals
  materialize as PRs (git-native) or writes (hosted).
- Personal workspaces: identical, against `<user>/ai-registry`.

## 7. Local flow (developer, outside ascent's control)

`git clone` the registry → edit `skills/x/SKILL.md`, bump `version`, append `LESSONS.md` → PR →
CODEOWNER merges → webhook → indexer → `catalog.json` → every repo's next `npx ascent skills sync`
(or plain `git pull` in a subtree/submodule setup) picks it up. Hooks (`npx ascent hooks install`)
append invoke events locally; `report` (or `sync`) ships counts to the API or the registry folder.
Nothing in this path needs an ascent session; ascent needs only read access to the registry.

## 8. Distributable (`npx ascent`)

Extract `scripts/ascent-skills.mjs` into a published package (`packages/ascent-cli`, zero-dep,
Node 18): `skills sync|push|status|report`, `hooks install|remove`, `mentor init|share`, `registry
init` (scaffold locally + open PR via `gh` if present). Reads `.ai/manifest.yaml` for the pointer;
`ASCENT_TOKEN` optional (needed only for API sink / PR-by-token / share).

## 10. Prototype protocol (both tabs)

- One git worktree per tab (`.claude/worktrees/prototype-registry`, `…/prototype-care`), branched from
  HEAD; the main checkout carries foreign WIP and is not touched.
- Wire the tab for real (ORG_TAB_IDS, `ORG_NAV_GROUPS` Shared group, `MIGRATED_ORG_TAB_IDS`,
  `PERSONAL_TAB_IDS` for `care` (+ `registry`), `OrgTabChunks` branch, legacy redirect route stub) so
  the variants render inside the actual shell at `/org/<slug>?tab=registry`.
- `RegistryPanelSwitcher.tsx` / `CarePanelSwitcher.tsx` (client) hold the variant state; each variant
  is its own file (+ co-located sub-components); every `.tsx` ≤ 300 LOC; brand primitives only.
- Fixture view models live in `src/lib/org/registry-view.fixture.ts` / `care-view.fixture.ts` and
  are selected by `?demo=<state>`; the real loader returns `unmapped` / empty until R2/C3 land.
- Exit: `npx tsc --noEmit` clean, the 300-LOC check returns zero rows, `orgTabs.test.ts` green.
