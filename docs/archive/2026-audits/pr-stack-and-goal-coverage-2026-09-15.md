## 3. Why none of section 2 was applied

The local dev-tools HTTP surface exposes `POST /ideas`, `POST /kpis` and `POST /kpis/<id>/measure`.
There is **no goals endpoint** — `GET/POST/PATCH /dev-tools/goals` all return 404, and there is no
`/dev-tools/ideas/<id>`. Attaching an existing idea to a goal means setting `dev_ideas.goal_id`, and
the only path to that column is a direct write to the operator's live `personas.db`.

Re-filing through `POST /ideas` would not work either: existing rows carry dedup keys of the form
`scan:app-master:all:<title-slug>`, so a re-file from a different origin creates a **new** row rather
than updating the old one — which is precisely the "file no new ideas" constraint this pass was run
under, and would have grown the 32:1 backlog it was meant to hold flat.

So this pass proposes the mapping and leaves the write to the operator.

**The smallest thing that would close this gap for good:** a `PATCH /dev-tools/ideas/<id>` accepting
`{"goal_id": "..."}`. Without it, goal coverage can be measured but never repaired by an unattended
pass, and every reading will keep reporting the same eight uncovered goals.
