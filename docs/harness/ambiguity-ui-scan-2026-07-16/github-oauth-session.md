# GitHub OAuth & Session — ambiguity+ui scan (2026-07-16)

## 1. `/api/auth/session` answers only for the dormant auth stack — under the active Supabase wall it always says "signed out"
- **Severity**: High
- **Category**: undocumented-assumption
- **File**: `src/app/api/auth/session/route.ts:19`
- **Scenario**: The endpoint resolves `getSessionState()` from `src/lib/auth.ts`, whose first line is `if (!isAuthConfigured()) return { session: null, status: "none" }` (`src/lib/auth.ts:259`). Prior audits established `.env.production` has no `GITHUB_OAUTH_*`/`AUTH_SECRET`, so in prod this route unconditionally returns `{ status: "none", login: null, ... }` for a user who IS signed in via the active Supabase wall. The header comment sells it as the way for "client components, the badge/CLI integrations, and 'your session expires in N minutes' nudges" to ask "am I still signed in" — a promise that is false in exactly the deployment that matters. A grep shows zero in-repo consumers, so it is also a dead surface whose first future consumer will silently read every prod viewer as anonymous.
- **Root cause**: The route predates the Supabase layering and was never taught about `getViewer()`/`authGateEnabled()` (`src/lib/access.ts`); nothing in the file records that it only reflects the dormant custom-OAuth cookie.
- **Impact**: Any badge, CLI integration, or "session expiring" nudge built on this endpoint will report signed-in Supabase users as signed out in production — the same class of dual-stack rot that already caused the `readableOrgForOwner` lockout documented in `src/lib/auth.ts:329-352`. The comment's claim that "a periodic client poll also slides the inactivity horizon forward" is likewise inert under the active wall.
- **Fix sketch**: Make the route dual-stack like `resolveViewerLogin()`: when `authGateEnabled()`, resolve `getViewer()` and report the Supabase identity (login/name/avatar; expiry from the Supabase session if wanted), falling through to `getSessionState()` otherwise. At minimum, add a header comment mirroring the `readableOrgForOwner` KNOWN-FACT note so the next consumer isn't misled.

## 2. Supabase sign-in failure flag `?auth_error=1` is rendered nowhere — a silent dead-end the code claims the UI surfaces
- **Severity**: High
- **Category**: missing-state
- **File**: `src/app/auth/callback/route.ts:35`
- **Scenario**: When the PKCE code exchange fails (or the callback arrives with no code), the route redirects to `/?auth_error=1` with the comment "send the user home with a flag the UI can surface." A repo-wide grep for `auth_error` finds only this one line — no page or component ever reads it. The user who just failed to sign in lands on the home page, signed out, with zero feedback. Contrast the dormant custom flow, which distinguishes `denied` / `csrf` / `oauth` / `oauth_failed` / `not_configured` on `/connect` (`src/app/api/auth/login/route.ts:21`, `src/app/api/auth/callback/route.ts:66,77,83,149`) precisely so a cancel isn't misreported as an attack. The ACTIVE flow — the only one users hit in prod — collapses user-cancelled, expired code, and exchange failure into one unconsumed bit.
- **Root cause**: The flag was minted on the redirect side but the consuming banner was never built; the comment asserts the missing half exists.
- **Impact**: Every real-world Supabase sign-in failure (consent-screen cancel, expired code, Supabase outage) is a silent dead click at page-navigation scale: the user clicked "Sign in with GitHub", bounced through two providers, and arrived back exactly where they started with no explanation — the same "silent dead click" failure the `SupabaseSignInButton` comments (`src/components/SupabaseAuthButtons.tsx:44-48`) were explicitly fixed to avoid at the button layer.
- **Fix sketch**: Render a dismissible `role="alert"` banner on the home page (or wherever `next` pointed — carry it through: `/?auth_error=1&next=...`) when `auth_error=1` is present; distinguish at least `denied` (GitHub `error=access_denied` param, currently ignored) from exchange failure, mirroring the custom flow's taxonomy. Alternatively redirect to `/connect?error=oauth_failed`, which the connect page already knows how to display.

## 3. The entire onboarding/installation machinery exists only in the dormant callback — the active Supabase path silently skips it, undocumented
- **Severity**: Medium
- **Category**: trade-off-undocumented
- **File**: `src/app/auth/callback/route.ts:15` (vs `src/app/api/auth/callback/route.ts:86-146`)
- **Scenario**: The dormant custom callback does six consequential things at sign-in: upserts App installations for owner→installation resolution (`upsertInstallation`), stamps the revocation version (`getSessionVersion`), runs org auto-discovery, seeds the watchlist for the most-active org, routes first logins through the `/launch` cinematic, and supports the `resync=1` re-sync round-trip. The ACTIVE Supabase callback does exactly none of these — it exchanges the code and redirects. Neither file records this asymmetry: the Supabase callback's header describes only cookie mechanics, and the rich comments in the custom callback read as if they describe the product's live sign-in behavior.
- **Root cause**: The Supabase wall was layered on for authentication only, but the sign-in *moment* had accumulated product behavior (onboarding, discovery, install linking) that never moved with it; no comment or doc marks those behaviors as prod-dead.
- **Impact**: In prod, a brand-new user lands on a blank dashboard — the precise outcome `discoverOrgs` exists to prevent ("so a brand-new user doesn't land on a blank dashboard", `src/app/api/auth/callback/route.ts:108`). `/launch` stays unreachable (confirmed by the 2026-07-09 audit), installations are linked only via webhook/other paths, and future readers of the custom callback will reason from behavior that never executes. This is the same "comments describe the dormant stack" trap that finding 1 and the `readableOrgForOwner` incident stem from.
- **Fix sketch**: Add a short "DIVERGENCE" note atop both callbacks listing which sign-in behaviors run under which stack; then either port the still-wanted pieces (a post-login hook after `exchangeCodeForSession` could run discovery/seeding keyed on the Supabase identity's `user_name`) or explicitly retire `/launch`/resync/discovery with a dated decision record.

## 4. Both sign-in buttons stay stuck on the pending spinner after back-navigation (bfcache) — no reset path
- **Severity**: Medium
- **Category**: edge-case-gap
- **File**: `src/components/SupabaseAuthButtons.tsx:49` (also `src/components/GitHubSignInButton.tsx:49`)
- **Scenario**: Both CTAs set `pending=true` on click and deliberately never clear it on success ("keep the pending state until it leaves"). If the user reaches GitHub's consent screen and presses Back, Safari/Firefox (and Chrome for same-site history) restore the page from the back/forward cache with its JS state intact: the button is still `disabled`/`aria-disabled` with a spinner and "Redirecting to GitHub…", permanently. The `GitHubSignInButton` anchor additionally swallows all further clicks via `e.preventDefault()`. The only recovery is a manual reload — which nothing suggests.
- **Root cause**: The happy path (navigation completes) is the only path modeled; there is no `pagehide`/`pageshow` (`event.persisted`) listener to reset `pending` when the page is restored from bfcache.
- **Impact**: A user who backs out of the GitHub consent screen — a common second-thoughts flow, and the very users the least-privilege `read:user` scope change was made for — returns to a dead sign-in affordance on every gated page. `aria-busy` stays true forever, so screen-reader users hear a perpetual in-flight state.
- **Fix sketch**: In both components add `useEffect(() => { const h = (e: PageTransitionEvent) => { if (e.persisted) setPending(false); }; window.addEventListener("pageshow", h); return () => window.removeEventListener("pageshow", h); }, [])` — ideally in one shared hook next to the already-shared `buttonChrome.tsx` so the two wrappers can't drift (the stated purpose of that file).

## 5. SignInNotice promises "access private repositories" identically for both backends — untrue for a bare Supabase login
- **Severity**: Low
- **Category**: visual-inconsistency
- **File**: `src/components/SignInNotice.tsx:41-45`
- **Scenario**: The notice body ("Connect your GitHub account to access private repositories, history, and usage") is the same whether the CTA drives the dormant custom OAuth or the active Supabase wall. Under the custom flow that copy is accurate — the callback loads App installations that gate private-org reads. Under the active Supabase wall, signing in only authenticates identity; private-repo access still depends on the GitHub App installation resolved elsewhere (`canReadOrg`), so a user without the App installed signs in and still sees public data — the copy over-promised. Relatedly, the two flows' `safeNext` fallbacks diverge (`/connect` default in `src/lib/auth.ts:440` vs explicit `"/"` in `src/app/auth/callback/route.ts:18`), so a stripped `next` lands users in different places per backend.
- **Root cause**: The notice was made backend-aware for *which button* to render (the `provider` prop fix documented in its own comment) but not for *what the sign-in grants*; the copy predates the Supabase layering.
- **Impact**: Mild but real expectation mismatch at the most conversion-sensitive moment: users sign in expecting private-repo access and may read the still-public view as a bug. The divergent `next` fallback also makes post-login landing behavior inconsistent between stacks for the same edge case.
- **Fix sketch**: Vary the body copy by `backend` (Supabase: "Sign in with GitHub to access your history and usage. Private repositories additionally require the Ascent GitHub App." or similar), and pass a single shared fallback into both `safeNext` call sites so the stacks land users consistently.
