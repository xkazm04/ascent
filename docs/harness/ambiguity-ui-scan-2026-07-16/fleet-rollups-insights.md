# Fleet Rollups & Insights — ambiguity+ui scan (2026-07-16)
> Total: 5 (Critical: 0, High: 2, Medium: 3, Low: 0)

## 1. Plan retention floor clamps the trend but not the baseline/movers — deltas read history the tier doesn't buy
- **Severity**: High
- **Category**: trade-off-undocumented
- **File**: `src/lib/db/org-rollup.ts:396` (clamped trend) vs `src/lib/db/org-rollup.ts:441` (unclamped baseline); also `src/lib/db/org-insights.ts:106` (movers pre-start query)
- **Scenario**: `getOrgRollup` clamps the trend's lower bound to `retentionCutoff(org.plan)` ("a NON-DESTRUCTIVE read floor — the trajectory looks back only as far as the tier buys"), and `getOrgRepoHistories` does the same. But the baseline query (`scannedAt: { lt: start }`) and `getOrgMovers`' pre-start query have no retention clamp: on a Free plan (30d retention) with a 90d/quarter window, the headline `deltas`, `dimDeltas`, `baseline.asOf`, and every mover are computed against scans up to arbitrarily old — history the same page's trend refuses to draw.
- **Root cause**: The retention policy was retrofitted onto the two trend-shaped reads; nobody recorded whether period-over-period comparison is *inside* or *outside* the entitlement, so the other four window consumers silently kept the unlimited read.
- **Impact**: Either a plan-entitlement bypass (Free orgs get 90d comparisons Pro pays for) or, if intentional, an undocumented exception that will be "fixed" one day and silently null out every Free-tier delta tile. Also visibly incoherent: a chart that starts 30d ago sits beside a tile captioned "vs 90d ago".
- **Fix sketch**: Decide and record the policy in one place. If deltas are entitlement-gated, clamp `start` once (`const effStart = maxDate(retentionStart, start)`) before both the baseline and movers queries and surface "limited by plan" in `comparisonLabel`; if not, add a comment on the baseline query stating retention deliberately caps trend depth only, and pin it with a test.

## 2. The Teams tab is the only fleet surface that ignores the period selector — "since last scan" masquerades as the selected window
- **Severity**: High
- **Category**: undocumented-assumption
- **File**: `src/lib/db/org-teams.ts:326` (no `OrgWindow` param); contrast `src/lib/org/period.ts:18` ("Use on EVERY org tab that scopes data to the selected window")
- **Scenario**: `getOrgTeamRollup` takes segment/tech-group scopes but no window. Team movers (`improving`/`declining`/`avgDelta`, org-teams.ts:178) always compare each repo's latest two scans, whatever their spacing — for a daily-scanned repo that's a 1-day delta, for a quarterly one a 90-day delta — while every sibling aggregate (rollup, movers, engine mix, recs-actioned) re-scopes to the user's chosen 30d/90d/quarter. Changing the period selector changes every tab except Teams, with no cue.
- **Root cause**: C6 was built on the pre-window "since last scan" semantics and was never threaded through the `OrgWindow` plumbing when the period system landed; the `TeamRollup.avgDelta` doc says "since last scan" but the UI context implies the dashboard period.
- **Impact**: A leader reading "Quarter in review" sees team momentum numbers that are neither quarter-scoped nor even mutually comparable across teams (each delta spans a different, cadence-dependent interval). Cross-team `improving/declining` counts are apples-to-oranges.
- **Fix sketch**: Either thread `OrgWindow` into `getOrgTeamRollup`/`rollupTeams` (baseline = latest scan `< start`, matching `getOrgMovers`' reconciled half-open semantics), or label the team movers block explicitly ("since each repo's previous scan — not period-scoped") so the mismatch is at least declared.

## 3. CHAMPION_MIN_POP's "apply IDENTICALLY everywhere" contract is broken on TeamsStandings (and the guard there is a constant-true no-op)
- **Severity**: Medium
- **Category**: missing-state
- **File**: `src/components/org/shared/champions.ts:7`; violation at `src/components/org/teams/TeamsStandings.tsx:54` and `:163`
- **Scenario**: `champions.ts` documents that the ≥3-contributor population floor "must be applied IDENTICALLY everywhere champions are surfaced (Contributors, Adoption, Teams) so the org can't dodge it on one tab". Contributors (`contributors/page.tsx:251`), Adoption (`adoption/page.tsx:64`), and TeamsMatrixDetail (`:72`) all gate on it. TeamsStandings gates only on `standing.champions.length > 0 && standing.aiCommitShare > 0` — a 1-person team's sole AI user is named a champion there. Its only use of the constant is `{CHAMPION_MIN_POP > 0 && "…"}` — a compile-time-true condition guarding a caption, which reads like a gate but isn't. Relatedly, `rollupTeams` (org-teams.ts:215) picks team champions with `aiCommits > 0` and no ≥3-commit volume floor, unlike `getContributorInsights` (`commits >= 3 && aiCommits > 0`, org-contributors.ts:142).
- **Root cause**: The gate lives in each rendering call site rather than in the data layer or a shared `championsFor(team)` helper, so a new champion surface can (and did) omit it.
- **Impact**: Exactly the "surveillance-y ranking / success theater" the constant exists to prevent — one tab names an individual the others deliberately withhold, and a 1-commit contributor can headline a team's standings card.
- **Fix sketch**: Move the gate into the producer (empty `champions` array when `contributors < CHAMPION_MIN_POP` in `rollupTeams`/`getContributorInsights`), or add the `standing.contributors >= CHAMPION_MIN_POP` check to TeamsStandings and delete the no-op `CHAMPION_MIN_POP > 0 &&`. Align the volume floor (≥3 commits) across both champion pickers or record why teams differ.

## 4. Backlog due-date buckets use UTC calendar days while the whole window system uses LOCAL days — and "Due this month" is really "≤31 days"
- **Severity**: Medium
- **Category**: edge-case-gap
- **File**: `src/lib/db/org-insights.ts:287-305` (`daysUntil`/`dueBucketFor`); contrast `src/lib/window.ts:66` and `src/lib/db/org-rollup.ts:303`
- **Scenario**: The dashboard's time semantics were deliberately unified on LOCAL calendar days (window `startOfDay`, trend `localDayKey` — both carry fix-comments about the UTC/local split). The backlog's `daysUntil` computes whole days via `Date.UTC(getUTC*…)`: on a non-UTC server, an item due "today" local can bucket as `overdue` (or vice versa) for hours around midnight, and the overdue count in the header disagrees with the day boundary every other number on the page uses. Separately, `this_month` means "within 31 rolling days" but renders as the label "Due this month" (`DUE_BUCKET_LABEL:279`) — on July 1 an item due July 29 and one due Aug 1 land in different buckets under a calendar-month reading, same bucket here.
- **Root cause**: `dueBucketFor` predates (or ignored) the local-day unification; the 7/31 cutoffs were chosen as magic numbers without recording whether buckets are rolling or calendar-aligned.
- **Impact**: Off-by-one overdue/this_week classification for any deployment or user west/east of UTC — the highest-stakes bucket (Overdue drives the owner sort at org-insights.ts:509) is the one that flips. Label/semantics mismatch erodes trust in the planning surface.
- **Fix sketch**: Compute `daysUntil` from local-midnight timestamps (reuse `startOfDay` math from window.ts) to match the rest of the dashboard, or record why due dates are intentionally UTC (they're stored as date-only). Rename labels to "Due within 7 days" / "Due within a month", or align cutoffs to calendar week/month — pick one and pin with a test alongside the existing `dueBucketFor` unit tests.

## 5. Contributor/team AI-share aggregates sum per-repo snapshots captured at different scan times, with no staleness horizon
- **Severity**: Medium
- **Category**: undocumented-assumption
- **File**: `src/lib/db/org-contributors.ts:55-90` (and `src/lib/db/org-teams.ts:350` `contributors` select)
- **Scenario**: Each `RepoContributor` snapshot reflects "the recent-activity window we capture at scan time" — a window anchored to that repo's *own* last scan. `getContributorInsights` and `rollupTeams` sum `commits`/`aiCommits` straight across repos, so a repo last scanned 14 months ago injects its stale activity into `orgAiShare`, `championScore`, `aiActiveShare`, team `knowledgeScore`, and `busFactor`/`soloMaintainer` with the same weight as yesterday's snapshot. `getOrgActivity` hit this exact class and grew `ACTIVITY_HORIZON_WEEKS = 26` (org-signals.ts:280, "one repo last scanned long ago can't… dilute the trend"); the contributor path has no equivalent, and nothing in the returned shape tells the UI how stale the blend is.
- **Root cause**: The "no extra GitHub calls, latest snapshot per repo" design is documented, but the cross-repo *heterogeneous-recency* consequence isn't — the implicit assumption "all repos are scanned on a similar cadence" is unstated and false for mixed-schedule fleets.
- **Impact**: An engineer who left a year ago can remain the org's #1 AI champion via one unscanned repo; `soloMaintainer`/`busFactor` risk flags describe a team composition that no longer exists; team `knowledgeScore` (50% aiCommitShare) inherits the skew and can crown a stale knowledge leader.
- **Fix sketch**: Mirror the org-signals fix: drop (or down-weight) snapshots whose scan is older than a horizon anchored at the fleet's newest scan (`lastActiveAt`/scan `scannedAt` is already selected), and expose a `staleRepos` count so the UI can annotate. Minimum: document the mixed-window semantics on `ContributorInsights` and surface "as of each repo's last scan" copy where champions and bus-factor render.
