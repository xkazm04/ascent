## 1. The published methodology (the "transparent, defensible" rubric doc) no longer matches the math the engine actually runs
- **Severity**: High
- **Category**: doc-drift
- **File**: `docs/MATURITY_MODEL.md:135` (§3 formula block) vs `src/lib/scoring/engine.ts:80`, `src/lib/scoring/engine.ts:115`, `src/lib/maturity/model.ts:278`
- **Scenario**: The doc opens with "this is the core IP … intentionally transparent so scores are defensible" and publishes the scoring formula: `dimensionScore = round(BLEND * llmScore + (1-BLEND) * signalScore)` with a fixed ±N guardband, and `overall = round(Σ weight(D) * dimensionScore(D))`. The engine actually does four things the doc never mentions: (a) the blend is coverage-scaled — `effectiveBlend = SCORE_BLEND * clamp(coverage)` (engine.ts:81), so a half-inspected repo leans harder on signals; (b) the guardband is **doubled** (±50, not ±25) for any dimension the LLM's self-audit flagged as a detector discrepancy (engine.ts:115); (c) the overall is a **renormalized archetype-weighted mean over present dimensions** (`overallScoreFor`), not a raw weighted sum over the base weights — the doc's §2b mentions the lens but §3's formula still shows the un-lensed sum; (d) D9 is fully deterministic — the LLM never moves it (engine.ts:119, scan.ts:256), while §3 implies every dimension blends. The §4 example also shows `"weight": 0.18`, a value no lens contains.
- **Root cause**: The engine gained coverage-weighting, discrepancy-widened guardbands, renormalization, and deterministic D9 across several fix waves; §3 of the doc (and the pseudo-code that customers/auditors are pointed at) was never updated.
- **Impact**: Anyone auditing a score against the published rubric — the product's stated defense of its credibility — computes a different number than the engine produces. A partial-coverage or discrepancy-flagged scan can deviate from the documented formula by up to 25 points on a dimension with no documented explanation, which reads as a scoring bug rather than a design choice.
- **Fix sketch**: Update §3's pseudo-code to the real pipeline (coverage-scaled blend, per-dimension guardband widening on flagged discrepancies, renormalized lens-weighted mean over present dims, deterministic D9), fix the `0.18` example weight, and add one line per mechanism to "Design principles". Cheap insurance: a test asserting the doc quotes `SCORE_BLEND`/`LLM_GUARDBAND` values that match the constants.

## 2. `reviewedRate` has no minimum-sample floor, so a single unreviewed merged PR drags D6 by design — the exact hazard `aiGovernedRate` was floored against
- **Severity**: High
- **Category**: edge-case-gap
- **File**: `src/lib/analyze/pulls.ts:133` (rate), `src/lib/analyze/pulls.ts:179` (fold into D6)
- **Scenario**: `aiGovernedRate` carries a documented ≥5-AI-PR floor (pulls.ts:147-148) with explicit reasoning: "a single unreviewed AI PR in a 3-PR window swings the rate ~33pts and can flip the rigor axis / posture near the 50 threshold." But `reviewedRate` — which feeds `prRigor` at 0.5 weight and then blends into D6 at 0.35 (pulls.ts:183, 190) — computes from as few as **one** human-merged PR. A repo whose recent window contains a single self-merged PR gets `reviewedRate = 0`, `prRigor ≈ 0.3*smallPrRate + 0.2*stability`, and D6 dragged toward it, potentially flipping the rigor axis and posture off a 1-PR sample. Same class of hazard, guarded on one rate and not its sibling.
- **Root cause**: The sample-size lesson was applied where it was first observed (aiGovernedRate) but the identical statistical exposure in `reviewedRate`/`prRigor` was never revisited; only `pr.analyzed === 0` gates `applyPrSignals`.
- **Impact**: Small or bursty repos (exactly the "solo/early" population the archetype lens tries to treat fairly) get a rigor-axis penalty derived from a 1–4 PR sample, which can flip the posture quadrant near the 50 threshold — a headline-visible misclassification from statistically meaningless data.
- **Fix sketch**: Apply a floor consistent with the aiGovernedRate reasoning: `reviewedRate = mergedHuman >= 5 ? pct(...) : null` (the null path already exists and renormalizes prRigor over smallPrRate/stability), or scale the D6 blend weight by `min(1, mergedHuman/5)`. Record the chosen floor's rationale next to the aiGovernedRate comment so the two stay in lockstep.

## 3. Nothing enforces the SCORING_RUBRIC_VERSION bump the cache correctness depends on
- **Severity**: Medium
- **Category**: undocumented-assumption
- **File**: `src/lib/maturity/model.ts:27` (and consumers `src/lib/cache.ts:63`, `src/lib/scan-cache.ts:55`)
- **Scenario**: The constant's doc-comment correctly states the failure it prevents: forget to bump after editing any score-moving knob (weights, bands, blend, guardband, prompt criteria, detector points) and "stale scores are served as current" for up to 7 days fleet-wide. Yet the version is still `"r1"` after a long series of score-moving detector/prompt changes visible in the code's own changelog comments (coverage-scaled blend, D2 assertion penalty, D3 off-GitHub CI credit, D4 false-positive fixes, widened guardband), and nothing — no test, no CI check — ties the constant to the knobs it versions. `scan-cache.ts:55` additionally notes a rubric bump can't even be detected per-row there.
- **Root cause**: The invariant lives entirely in a comment; the bump is manual discipline with no mechanical backstop, and detector-level point changes (docs/CALIBRATION.md's own tuning loop, step 3) aren't explicitly listed as bump triggers, leaving it ambiguous whether they require one.
- **Impact**: One forgotten bump silently serves pre-change scores as current across every cached repo — the precise failure the constant exists to prevent, with no signal that it happened. Trend comparisons then mix rubrics without any marker.
- **Fix sketch**: Add a snapshot test that hashes the rubric surface (DIMENSIONS weights+criteria, LEVELS bands, SCORE_BLEND, LLM_GUARDBAND, POSTURE_THRESHOLD, ARCHETYPE_WEIGHTS, the SYSTEM prompt string, and ideally the detector point tables) and fails with "rubric changed — bump SCORING_RUBRIC_VERSION and update this hash". Also settle in the comment whether detector point tweaks (calibration step 3) count as rubric changes.

## 4. POSTURE_THRESHOLD=50 is misaligned with the L3 band floor (45), so a repo can be "Augmented" and "Getting Started" in the same report
- **Severity**: Medium
- **Category**: magic-number
- **File**: `src/lib/maturity/model.ts:337` (threshold) vs `src/lib/maturity/model.ts:59` (L3 band `[45, 64]`)
- **Scenario**: A repo scoring 45–49 on both axes rolls up to an overall in the L3 band — "Augmented: AI is part of the team's standard workflow… AI-generated code is safe to merge" — while `postureFor(47, 47)` returns "Getting Started: early on BOTH AI adoption and engineering rigor." The two headline artifacts on the same report hero directly contradict each other. Neither the code nor docs/MATURITY_MODEL.md §2b records why the posture cut is 50 rather than aligned to the L3 floor (or any rationale for 50 at all).
- **Root cause**: The level bands and the posture quadrant threshold were defined independently; 50 is a round-number default whose relationship to the band edges was never reasoned about in writing.
- **Impact**: In the 45–49 corridor (a common landing zone for mid-maturity repos) the report asserts both "AI is part of the standard workflow" and "early on both axes," undermining exactly the credibility the transparent rubric is supposed to buy. Users near the boundary also see posture flip on ±1-point noise with no hysteresis.
- **Fix sketch**: Either align `POSTURE_THRESHOLD` with the L3 band floor (45) so "Getting Started" ⇔ sub-Augmented, or keep 50 and document the deliberate trade-off ("posture is a stricter bar than the level") in the model file and MATURITY_MODEL.md §2b — plus consider labeling the 45–55 corridor as "borderline" in the UI rather than asserting a confident quadrant.

## 5. `classifyArchetype` equates popularity with run-style: 1000 stars forces the org lens onto a solo repo, with no recorded rationale for the 1000/50 cutoffs
- **Severity**: Medium
- **Category**: undocumented-assumption
- **File**: `src/lib/analyze/index.ts:894`
- **Scenario**: The archetype lens exists so "single-author work is judged fairly rather than being dragged to L1–L2 for lacking infrastructure it doesn't need" (model.ts:243-245). But classification is `stars >= 1000 → org`, `stars >= 50 → team`, ignoring the contributor data the scan already computes (`computeContributors`, same file). A viral single-maintainer repo (a very common OSS shape) crosses 1000 stars and is judged under the org lens — D3 doubles (0.07→0.14), D4 +5pts, D9 more than doubles (0.04→0.09) — re-introducing the exact unfairness the lens was built to remove. The thresholds 1000 and 50 carry no comment, doc, or calibration note explaining their choice; MATURITY_MODEL.md §2b only says "from CODEOWNERS, CI workflows, stars."
- **Root cause**: Stars were the cheapest available proxy at build time ("no extra API calls"), and the heuristic was never revisited against the contributor signal that later became available in the same snapshot, nor were its magic cutoffs given recorded reasoning.
- **Impact**: Popular solo projects are systematically down-scored on infrastructure dimensions (and their ARCHETYPE_HINT tooltip then asserts they're "judged at platform/org scale," which is visibly wrong to the owner). Since the archetype changes weights, this is a silent, unexplained score shift of potentially several points and a band.
- **Fix sketch**: Fold contributor count into the heuristic (e.g. `contributors.length` from recent commits: 1–2 active authors caps the archetype at "team" regardless of stars; org requires CODEOWNERS/workflows OR ≥N active contributors), document the chosen thresholds and their reasoning next to the function, and add the star-only-solo case to the calibration bench set so the cutoffs become tuned rather than assumed.
