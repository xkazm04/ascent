# GitHub App Installation & Webhooks — ambiguity+ui scan (2026-07-16)
> Total: 5 (Critical: 0, High: 3, Medium: 2, Low: 0)

## 1. Installing the GitHub App silently mints a `private`-plan org row — an undocumented entitlement grant with an asymmetric update path
- **Severity**: High
- **Category**: undocumented-assumption
- **File**: `src/lib/db/installations.ts:23`
- **Scenario**: `upsertInstallation` creates a brand-new Organization with `plan: "private"` for any account that installs the App (via `/api/app/setup` or the `installation.created` webhook). But the `update` object (line 17) deliberately-or-accidentally omits `plan`, so an org that already exists as `"free"` keeps `"free"` after installing, while a first-time installer gets `"private"` immediately. Nothing in the file, the setup route, or `docs/GITHUB_APP.md` records whether installing the App is *supposed* to confer the private plan, or why create and update diverge.
- **Root cause**: The plan value is a hardcoded magic string chosen when installations implied paying customers; the billing system (Polar, `POLAR_PLAN_PRODUCTS`) later became the plan authority, and no one recorded which source wins. The create/update asymmetry encodes a decision ("never downgrade/overwrite an existing plan") that is invisible unless you diff the two objects.
- **Impact**: Two accounts doing the same action end in different plan tiers depending on row-existence order — e.g. an account first seen via a public scan (free row) then installing gets `free`, a fresh installer gets `private`. If `private` gates any paid feature, install order becomes an unintended entitlement bypass or an unintended lockout; support cannot reason about it because the rule exists only in code.
- **Fix sketch**: Extract `const INSTALL_DEFAULT_PLAN = "private"` with a comment stating the decision ("installation implies private-repo access intent; billing may later override; existing plans are never touched by installation events — see <billing module>"), or better, stop setting `plan` here and let the billing layer own it, defaulting new rows to the platform default plan.

## 2. Org rename / installation transfer splits one installation across two org rows — the login-as-primary-key trade-off is unhandled and unrecorded
- **Severity**: High
- **Category**: edge-case-gap
- **File**: `src/lib/db/installations.ts:15`
- **Scenario**: The org slug IS the lowercased GitHub login. When a GitHub org renames (`acme` → `acme-inc`), the next webhook/setup for the same `installation_id` upserts a NEW row `acme-inc` (fresh `private` plan, no watched repos), while the OLD `acme` row silently keeps the same `githubInstallId`, its watch flags, and its scan schedules. Nothing ever detects or merges the pair. `removeInstallation`'s `findMany` (installations.ts:52) even anticipates multiple rows per install id — but only for teardown; the live-traffic paths (`getInstallationIdForOwner`, webhook owner-matching, `getRepoStates(orgLogin)`) all key on login and now disagree about which row is real.
- **Root cause**: "login == slug == tenant identity" was a reasonable bootstrap assumption, but GitHub logins are mutable while `installation.id` is the stable key. The trade-off (simple owner→install resolution vs. rename fragility) was never written down, and no `installation.renamed`-adjacent handling exists.
- **Impact**: After a rename, pushes deliver payloads with the new owner login: `isRepoWatched(newSlug, ...)` finds nothing, so every watched repo silently stops auto-rescanning; scheduled rescans on the stale row keep minting tokens and scanning under the dead slug; history/KPIs fork across two tenants. Symptoms look like random scan loss, days after the rename.
- **Fix sketch**: Before creating in `upsertInstallation`, look up an existing org by `githubInstallId` — if found under a different slug, either migrate the row (rename slug, keep watch/schedule/report FKs) or log loudly and refuse to fork. Record the identity decision in the file header ("installation id is the stable key; login is display + routing only").

## 3. Fork-PR fallback posts a default-branch verdict as the PR's required check, with no visible signal it never scored the PR
- **Severity**: High
- **Category**: trade-off-undocumented
- **File**: `src/app/api/app/webhook/route.ts:247-287`
- **Scenario**: When the PR head is unreachable via the base repo's tree API (typical for fork PRs), `runPrGate` falls back to scanning the default branch and sets `scoredHead = false` — but then still evaluates the gate on that report and posts a normal success/failure Check Run attached to `headSha`. `buildGateComment` receives no `scoredHead` flag, so the check title/summary read as a verdict on the PR while actually describing the base tree (only the baseline diff is suppressed).
- **Root cause**: The fallback comment documents the availability trade-off ("so the check still posts") but not the integrity trade-off: a gate that scores the base branch structurally cannot fail on anything the PR itself changes.
- **Impact**: If this Check Run is used as a required merge status (the file's own GATE-3 comments say it is), every fork PR passes/fails based on the current default branch — a fork PR deleting the test suite or CI config sails through green, and the author sees a confident verdict about a tree that isn't theirs. Conversely a red default branch blocks an innocent fork PR with no explanation.
- **Fix sketch**: Thread `scoredHead` into the check output: on fallback, post conclusion `neutral` (or at minimum prepend "Scored the default branch — the PR head was unreachable (fork PR); this verdict does not reflect the PR's own changes") and skip the sticky comment's per-PR framing. Document in the fallback comment that a required-status consumer must treat fallback verdicts as non-authoritative.

## 4. Delivery is claimed for 24h before the body is parsed — a parse 400 or a claim-store error strands the delivery in a half-claimed state
- **Severity**: Medium
- **Category**: edge-case-gap
- **File**: `src/app/api/app/webhook/route.ts:509-521`
- **Scenario**: Two gaps in the otherwise meticulous claim/release choreography. (a) `claimWebhookDelivery` runs before `JSON.parse(raw)`; a parse failure returns 400 *without* `forgetDelivery`, so the id stays claimed for the full 24h `REPLAY_HORIZON_MS` and GitHub's retry of the 400 is answered `duplicate: true` — the event is dropped forever. (b) `deliveryAlreadySeen` optimistically inserts the id into the in-memory Map *before* the DB claim is attempted; if `claimWebhookDelivery` throws (DB blip), the route 500s (the throw is outside the lower try), GitHub redelivers, and the same instance now short-circuits on `seenLocally` — returning `duplicate: true` for a delivery that was never claimed nor processed.
- **Root cause**: `forgetDelivery` was systematically added to every *deferred-work* failure path (per the #2/#3/#5 fixes), but the two synchronous early-exit paths between claim and dispatch were missed; and the Map write in `deliveryAlreadySeen` doubles as both "check" and "record" with no rollback concept.
- **Impact**: Low-probability (GitHub sends valid JSON; the DB usually answers) but the failure is the exact one the release-net was built to prevent: a silently lost installation/push/PR event with a `duplicate: true` audit trail that says everything worked.
- **Fix sketch**: Move `JSON.parse` above the claim (the body is already in memory and signature-verified), or call `forgetDelivery` in the 400 path; wrap `claimWebhookDelivery` in try/catch that deletes the optimistic Map entry and returns 500 unclaimed. One test each — the suite already has the harness for this shape.

## 5. suspend/resume predicates are asymmetric — suspend pauses `scanSchedule != "off"`, resume restores only `watched && scanSchedule != "off"`
- **Severity**: Medium
- **Category**: undocumented-assumption
- **File**: `src/lib/db/installations.ts:110-113` (vs `:133-136`)
- **Scenario**: `suspendInstallation` clears `nextScanAt` for every repo with `scanSchedule != "off"` regardless of `watched`; `resumeInstallation` re-arms only repos that are BOTH `watched: true` AND `scanSchedule != "off"`. Any repo in the state `watched: false, scanSchedule: "weekly", nextScanAt: <set>` gets paused by a suspend and is never re-armed by the matching unsuspend — its schedule is silently dead until some unrelated write resets `nextScanAt`.
- **Root cause**: The code relies on an unstated invariant — "a repo with a non-off schedule is always watched" — that is enforced nowhere in this module (both `removeInstallation` and `reconcileWatchedRepos` clear the pair together, suggesting the invariant is *intended*, but nothing prevents a UI/API path from unwatching without zeroing the schedule). The docblocks describe each function's own behavior precisely yet never state the invariant that makes them a true inverse pair.
- **Impact**: If the invariant ever breaks (a partial write, a future "pause watching but keep cadence" feature, manual DB surgery), a routine billing-lapse suspend/unsuspend cycle becomes a permanent, invisible schedule loss — precisely the "reversible pause destroyed state" bug class the #1 suspend fix was written to eliminate.
- **Fix sketch**: Make the predicates identical (`watched: true, scanSchedule: { not: "off" }` on both sides, since unwatched repos are never due anyway), and state the invariant in one place ("scanSchedule != off ⇒ watched; enforced by X") with a test asserting suspend→resume round-trips every row it touched.
