### (a) Can a user iterate scan -> apply -> rescan without leaving the module? What breaks "infinite"?

Inside the Live tab, YES for the self-hosted local path: Observatory select -> Inspector proposes batch -> Run -> Outcome -> "Back" keeps selection so the next run reuses it (`CockpitOutcome.tsx:3-5`, `LiveCockpit.tsx:176-180`). `settle()` calls `router.refresh()` so the field re-seeds from the new scans (`LiveCockpit.tsx:57-66`).

What stops it being "infinite":
1. **Every run is bounded and manual.** Cap 5 cycles/run (`loop-runs-types.ts:15`), one run per org at a time (`loop-engine.ts:94-95`), and the user must press Run again. The unbounded-until-target layer (drive) exists only as `curl`/companion API (`src/app/api/org/local/drive/route.ts:1-10`: "by an operator with curl or by the companion, without a tab open") and even it stops at 8 runs and on the first "dry" run (`drive.ts:93-98`).
2. **Drive state is process-local**: `drives` Map on `globalThis` (`drive.ts:121-124`); a restart ends the drive, and there is no boot-time stale-run sweep (`docs/features/org-planning/live.md:446-455`).
3. **Managed cloud has no loop at all**: `selfHostGuard` 404s every loop/drive route and the cockpit shows the "hosted" setup state (`CockpitSetup.tsx:37-58`; `live.md:448-450` "No hosted dispatch").
4. **Worktree rescans cannot see GitHub-side signals**: `scopeCaveat: "GitHub-side signals are not included"` (`loop-lane.ts:115`, `noAmbientToken: true` `:116`); the additive D2/D3/D4 folds from check-suites and Actions health (`src/lib/analyze/platform-signals.ts:3-14`) never apply, so the loop's own measurement is structurally capped below what a GitHub scan of the same commit would credit. The doc's green predicate is per-dimension L5 on every dimension (`green.ts:23-27`, per-dimension rationale `:9-12`) and a contested dimension is never green (`green.ts:108-112`), so a fleet can be un-greenable from inside the loop.
5. **Agent model is fixed** by `CLAUDE_MODEL` (default `sonnet`, `agent.ts:52`; gap listed in `live.md:459`); per-session timeout 20 min (`agent.ts:31-33`).
6. **The brief is about "codebase ready for automated LLM development"** but the loop's batch source is the scan backlog only (`openBatch` `loop-lane.ts:71-96`), and the `.ai/` foundation / practice PR machinery (steps 4a/4b) is a *different* door (GitHub App write, draft PRs) that the local loop never invokes. There is no path where the local agent installs the `.ai/` foundation; the foundation route requires `getScanReportByCommit` + App installation (`foundation/pr/route.ts:12-15`).

### (b) What produces L1..L5 and D1..D9

- Dimensions `D1..D9` with weights/axes: `src/lib/maturity/model.ts:204-300` (ids at `:206,216,226,235,249,258,268,278,288`). Overall = archetype-weighted mean (`overallScoreFor`, `:432-442`), rubric `r10` (`:97`), LLM blend `SCORE_BLEND = 0.6` (`:100`), guardband `LLM_GUARDBAND = 6` (`:131`).

- Pipeline: deterministic signals (`src/lib/analyze/**`) -> LLM assessment with retry/failover/mock floor (`src/lib/scan.ts:244-266`) -> `composeScanReport`. UAT L2 measured the LLM moving the score only ~±2 points (`uat/runs/2026-08-10-ascent-first/SUMMARY.md` item 6).
- "Green" for the loop = every dimension in L5 band, `GREEN_MIN_SCORE` derived from `LEVEL_BY_ID` (`src/lib/maturity/green.ts:23-27`).

### (c) How apply / foundation works and whether rescan reflects the lift

- Cloud: practice or foundation -> draft PR on the customer repo via installation token (`src/lib/practices/apply.ts:1-8`, `src/lib/standard/pr.ts:1-13`). Lift shows only after the PR merges and a GitHub-side scan runs: webhook push on default branch re-scans a watched repo (`src/app/api/app/webhook/route.ts:5`), cron rescan (`docs/features/fleet/rescan.md:3-6`), or the wall's ship-loop band verify-rescan on merge (`useShipLoop.ts:20-21`, refresh every 90 s `:11`).

- Honest-closure rule means a "lift" can be refused: no-movement keeps the row open (`followups.ts:98-100`).
